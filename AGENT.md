# AGENT.md

Рабочий документ проекта Cargo Optimizer: для того, кто продолжает работу, и для
AI-ассистента, которому дают доступ к репозиторию. Продуктовое описание и
инструкция запуска — в [README.md](README.md); здесь то, чего README не
объясняет: почему сделано именно так, что нельзя ломать и что делать дальше.

Правило документа: если решение требуется, а ответа нет в разделе «Открытые
вопросы», спросить заказчика или организаторов, а не додумывать.

---

## 1. Статус на 25.09.2026

Работает на демонстрационных данных, проверено на объёме года:

- калькулятор себестоимости: 11 статей, у каждой формула и источник числа;
- фасад маршрутизации с разбором, за счёт чего вариант выгоднее;
- ЭДО-ассистент: чек-лист готовности, статусы документов, подсказки по отказам;
- клиентский трекинг груза;
- бот: знакомство из трёх шагов, команды, уведомления без спама;
- мини-приложение: четыре экрана, тёмная и светлая темы, состояния загрузки,
  пустоты и ошибки;
- 10 тестов расчётной части, все проходят.

Написано, но выключено до ответов заказчика: адаптер 1С (OData и маппинг полей),
клиент API оператора ЭДО, движок Яндекс.Маршрутизации. Переключаются
переменными окружения, по умолчанию демо-режим.

Не закрыто: публикация по HTTPS и привязка мини-приложения к боту, проверка
сборки Docker (раздел 5.1).

## 2. Карта кода

| Путь | За что отвечает | Что важно знать |
|---|---|---|
| `backend/services/cost.py` | Ядро: себестоимость рейса | У каждой статьи есть формула и источник. Этот контракт ломать нельзя, на нём держится доверие к расчёту |
| `backend/services/routing.py` | Фасад над движком маршрутов | Свой VRP не пишем, ценность в объясняющем слое поверх чужой выдачи |
| `backend/services/edo.py` | Комплаенс по ЭПД | Только чтение. Создание и подписание документов от имени компании в MVP запрещено |
| `backend/services/catalog.py` | Контекст данных, постраничность, сводки | На годовом объёме нельзя отдавать всё разом: выдача страничная, сводка за период |
| `backend/services/tracking.py` | Клиентский срез по грузу | Себестоимость и маржа сюда не попадают: это экран для грузоотправителя |
| `backend/adapters/` | Источники данных | Имена сущностей 1С вынесены в `mappings/*.json`, хардкод под одну конфигурацию запрещён |
| `backend/bot.py` | Бот MAX | Правила против спама в разделе 4 |
| `backend/max_api.py` | Клиент MAX Bot API | В докстринге зафиксировано поведение API, проверенное живыми запросами |
| `backend/auth.py` | Подпись initData | Перед публикацией `AUTH_MODE=strict` |
| `frontend/` | Мини-приложение | Без бандлера: статика раздаётся тем же процессом, что и API |
| `tools/generate_dataset.py` | Генератор тестовых данных | Детерминирован по seed, сам датасет не коммитится |
| `tools/export_openapi.py` | Экспорт схемы API | Запускать после любой правки роутеров |

## 3. Границы MVP

**В MVP:** себестоимость рейса, ЭДО-комплаенс на чтение, сравнение маршрутов как
фасад над внешним движком, базовый трекинг для клиента.

**Не в MVP, осознанно:** телематика и детект слива топлива (нужно уже
установленное у заказчика оборудование), голосовой ассистент, геймификация и
рейтинг водителей, автоматическое оформление ЭТрН.

## 4. Инварианты, которые нельзя ломать

Каждый пункт появился из конкретной ошибки, а не из вкуса.

1. **У статьи затрат всегда есть формула и источник.** Иначе перевозчик не
   проверит расчёт и не станет ему доверять.
2. **Демо-данные всегда помечены:** поле `data_is_mock` в ответах API, строка
   под списком рейсов и в подсказке, пометка внутри датасета. Кричащую жёлтую
   плашку в шапке убрали: она удешевляла приложение, а честности хватает и
   спокойной пометки. Выдавать модель за работающую
   интеграцию нельзя ни в коде, ни в материалах.
3. **Уведомления не рассылают историю.** При регистрации пользователя весь
   накопленный backlog гасится (`db.prime_alerts`). Без этого новый подписчик
   получает сотни сообщений: на годовом датасете таких поводов 233.
4. **Одна сводка за цикл,** а не сообщение на каждое событие.
5. **Бот отвечает только на `message_created`.** На `message_edited` он
   дублировал ответы при каждой правке текста.
6. **Нативная кнопка `open_app` только после привязки мини-приложения
   организаторами** (`MINIAPP_REGISTERED=1`). С непривязанным адресом MAX
   отклоняет всё сообщение целиком (`404 Link not found`), и пользователь не
   получает ответа вовсе: так «умерли» «Понятно», «Пропустить» и повторный
   `/start`. До привязки кнопка «Открыть приложение» — обычная ссылка на ту же
   страницу. Обёртка `bot.send()` страхует: при отказе MAX переотправляет
   сообщение со ссылкой вместо нативной кнопки.
7. **Подтверждение нажатия всегда с `notification` и после ответа.** Пустое
   подтверждение MAX отклоняет с 400, и если слать его до следующего шага,
   исключение обрывает обработчик. Ответ через `message` в подтверждении
   запрещён: он заменяет исходное сообщение и уносит с ним меню.
8. **Журнал уведомлений ведётся для каждого пользователя отдельно,** ключ
   составной (`key`, `max_user_id`). С глобальным ключом второму пользователю не
   гасилась история, а рассылка падала на `UNIQUE constraint` у всех.
9. **На годовом объёме список не отдаётся целиком:** рейсы и документы
   постранично, сводка за период.
10. **Токен бота живёт только в `.env`,** который в `.gitignore`. В
    репозиторий, базу знаний и архив сдачи он не попадает.
11. **Статика мини-приложения отдаётся с версией в адресе** (`styles.css?v=<хэш>`),
    страница — с запретом кэширования (`backend/assets.py`). Без этого браузер
    внутри MAX держал старые css и js и после обновления показывал прежний сайт.
    Ссылки на `index.html` и статику руками не версионировать: версия считается
    из содержимого файла автоматически.

Проверка кнопок автоматизирована: `tests/test_bot.py` прожимает каждую
callback-кнопку бота против фейкового API, повторяющего оба найденных поведения
MAX. Кнопки мини-приложения проверяются прокликиванием в Chromium (Playwright).

## 5. Задачи

### 5.1. Проверить сборку и запуск в Docker

**Кому:** сокоманднику с рабочим Docker.
**Почему не сделано:** `Dockerfile` и `docker-compose.yml` написаны, но не
проверены: на машине, где велась разработка, демон не поднимается, в BIOS
отключена аппаратная виртуализация (SVM). Требование воспроизводимого запуска
обязательное, поэтому проверку нужно закрыть там, где Docker работает.

```bash
cp .env.example .env            # вписать MAX_BOT_TOKEN
docker compose up -d --build

curl http://localhost:8099/api/health          # ждём {"status":"ok"}
curl http://localhost:8099/api/summary         # ждём цифры по парку
docker compose logs --tail=20 app              # ждём "Бот запущен: @t459_hakaton_max_bot"
```

Критерии приёмки:

- [ ] образ собирается с нуля на чистой машине, без ручных шагов кроме `.env`;
- [ ] `/api/health` отвечает `ok`, мини-приложение открывается на `localhost:8099`;
- [ ] в логах видно подключение бота к MAX и работающий long polling;
- [ ] бот отвечает на `/start` в чате;
- [ ] после `docker compose restart` подписки и история расчётов на месте
      (подключён том `cargo-data`);
- [ ] правки в `Dockerfile` или `docker-compose.yml`, если понадобились, попали
      в репозиторий, README обновлён.

Большой датасет внутри контейнера, если понадобится:

```bash
docker compose exec app python tools/generate_dataset.py --trips 1200
# затем DEMO_DATA_FILE=data/demo_1c_large.json в .env и docker compose up -d
```

### 5.2. Опубликовать мини-приложение

1. Поднять решение на публичном HTTPS-адресе (годится адрес хостинга, свой
   домен не требуется).
2. Прописать адрес в `PUBLIC_WEBAPP_URL`, перезапустить сервис.
3. Отправить ссылку организаторам через форму сбора ссылок: привязку к боту
   делают они, административные настройки бота нам недоступны.
4. Переключить `AUTH_MODE` на `strict`.
5. Пройти сценарий внутри MAX с телефона.

### 5.3. Держать сервис живым на период проверки

Эксперты должны пройти сценарий в любое время. В compose уже стоят
`restart: unless-stopped` и healthcheck, но хостинг нужно выбрать так, чтобы
контейнер переживал перезагрузку машины.

### 5.4. Чек-лист перед сдачей

- [ ] `python tests/test_services.py` без провалов;
- [ ] `python tools/export_openapi.py`, схема соответствует коду;
- [ ] в README и `DATA-API.yaml` проставлен публичный адрес API;
- [ ] архив исходников с контрольной суммой SHA-256 и ссылка на репозиторий;
- [ ] в материалах явно указано, какие интеграции модельные.

## 6. Контракты интеграций

### 6.1. 1С, только чтение

**Канал:** HTTP-сервис или REST OData (1С 8.3.5+) как основной. Файловый обмен
выгрузками по расписанию — запасной путь: в логистике ИТ-служба часто не даёт
прямой доступ к базе, это закладываем сразу.

**Что тянем:** путевые листы (пробег план и факт, расход по норме и по факту),
заказы и договоры, тарифы и ставки, ГСМ-накладные, справочники ТС и водителей.

**Важно:** конфигурации у перевозчиков разные (УТ, УНФ, отраслевые ТМС). Имена
сущностей и реквизитов живут в `backend/adapters/mappings/<name>.json` и
настраиваются под заказчика. Файл `ut_11.json` — рабочая гипотеза под УТ 11, с
живой базой не сверялся.

### 6.2. ЭДО

К ГИС ЭПД напрямую не подключаемся: только через аккредитованного Минтрансом
оператора (Диадок, Контур, Astral, Такском, 1С-ЭПД). У операторов есть открытый
API под встраивание в чужую учётную систему.

**В MVP:** чтение статусов, чек-лист готовности компании, напоминания по
зависшим и отклонённым документам.

**Не в MVP:** создание и подписание документов от имени компании.

### 6.3. Маршрутизация

Свой VRP-солвер не пишем. Если у заказчика есть 1С:TMS, берём маршруты оттуда;
если нет, идём в API Яндекс.Маршрутизации или 2ГИС. Продукт добавляет
объясняющий слой: километры, литры, рубли, время и разбор, за счёт каких статей
вариант выгоднее. В самих движках этого в понятном пользователю виде нет, и это
и есть добавленная ценность.

## 7. Открытые вопросы

К заказчику:

1. Какая конфигурация 1С у пилотного заказчика и есть ли тестовый доступ?
2. С каким оператором ЭДО он работает или кого выбираем для пилота?
3. Нужен ли клиентский трекинг в MVP или переносим в Phase 2? Зависит от того,
   что важнее: экономия себе или прозрачность для его клиентов.
4. Есть ли установленная телематика (ДУТ, CAN)? Без неё контроль топлива на
   факте полностью уходит в Phase 2.
5. Актуальный тариф системы Платон на дату пилота: в расчёте стоит
   конфигурируемое значение 3,34 ₽/км на 1.09.2026.

К организаторам:

6. Формат `DATA-API.yaml`: файл собран по пунктам из FAQ. Если есть шаблон,
   перенесём значения в него.

## 8. Решения и их причины

| Решение | Причина |
|---|---|
| Backend на Python и FastAPI | Остальной стек команды на Python, схема OpenAPI генерируется из кода |
| Фронтенд без бандлера | Мини-приложение раздаётся тем же процессом, что и API; контракт не изменится при переезде на React |
| SQLite вместо PostgreSQL | В своей базе только подписки и история расчётов, источник правды остаётся за 1С |
| Слой адаптеров вместо хардкода 1С | Конфигурации у перевозчиков разные, хардкод сделал бы решение неприменимым у второго заказчика |
| ЭДО только на чтение | Подписание УКЭП от лица перевозчика юридически чувствительно, ошибка дороже отсутствия автоматизации |
| Схема MAX Bot API выяснялась запросами | Документация рендерится на клиенте; поведение проверено живыми вызовами, результат записан в `max_api.py` |
| Синтетический датасет | Открытых наборов с путевыми листами, ЭТрН, Платоном и нормами Минтранса нет |

## 9. Использование AI-инструментов

AI-ассистент применялся как вспомогательный инструмент: черновики кода, рутинные
правки, черновики документации, перебор вариантов при выяснении
недокументированного поведения MAX Bot API. Архитектурные решения, проверка
расчётов и поведение продукта остаются за командой, код разбирается и
поддерживается командой. Раздел держим честным: если он перестанет
соответствовать реальности, правим текст, а не реальность.
