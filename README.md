# Cargo Optimizer

Мини-приложение и бот в MAX для транспортной компании. Показывают, где рейс
теряет деньги, держат в порядке обязательные электронные перевозочные документы
и объясняют, какой маршрут выгоднее и почему.

**Бот:** [@t459_hakaton_max_bot](https://max.ru/t459_hakaton_max_bot)
**Трек:** транспорт и логистика

---

## Запуск мини-приложения за 3 команды

Нужен только Docker с Compose. Токен бота, доступ к 1С и прочие ключи для
мини-приложения **не нужны**: оно работает на встроенных демонстрационных
данных.

```bash
git clone https://github.com/SNSBlack/maxhak_cargo.git && cd maxhak_cargo
cp .env.example .env
docker compose up -d --build
```

Откройте в браузере **http://localhost:8099** — это мини-приложение целиком:
рейсы с разбором себестоимости, сравнение маршрутов, ЭДО и трекинг груза.
Окно удобнее сузить до ширины телефона (DevTools → режим устройства), интерфейс
рассчитан на мобильный экран.

Проверка, что сервис жив: `curl http://localhost:8099/api/health` должен вернуть
`{"status":"ok"}`. Документация API: http://localhost:8099/docs.

## Проблема

Четыре боли перевозчиков, с которых начинался проект:

1. **Топливо.** Перевозчик видит общий расход, но не понимает, где именно
   утекают деньги и сколько стоит конкретный перерасход.
2. **ЭДО-комплаенс.** С 1 сентября 2026 года электронные перевозочные документы
   обязательны (ФЗ №140-ФЗ), обмен идёт через ГИС ЭПД. Многие компании к сроку
   не адаптировались: документы висят без подписи, отклоняются из-за расхождений
   в реквизитах, часть водителей без УКЭП.
3. **Выбор маршрута интуицией.** Около половины перевозчиков выбирают маршрут
   не по себестоимости, потому что посчитать её на месте нечем.
4. **Непрозрачность для клиента.** Грузоотправитель не видит, где груз и из чего
   сложилась цена.

## Решение

**Ставка продукта: объяснимость.** Не «итого 32 563 ₽», а разбор по 11 статьям,
где у каждой видна формула и источник числа. Перевозчик не начнёт доверять
расчёту, который не может проверить руками.

| Экран | Что делает |
|---|---|
| **Рейсы** | Сводка за период, список рейсов с поиском, себестоимость любого рейса по статьям, калькулятор произвольного рейса |
| **Маршрут** | Сравнение вариантов в рублях, литрах и часах с разбором, за счёт каких статей один выгоднее другого |
| **ЭДО** | Готовность компании к обязательным ЭПД, документы, требующие действий, причина отказа и что чинить |
| **Груз** | Экран для грузоотправителя: стадия, срок прибытия, ставка, статусы документов |

Бот берёт на себя вход в приложение, короткие сводки в чате (`/trips`, `/money`,
`/edo`) и уведомления о новых проблемах.

Продукт сам находит то, что человек пропустил: убыточные рейсы, маржу ниже
порога окупаемости, перерасход топлива против нормы Минтранса, документы,
зависшие без подписи.

## Быстрый старт через Docker

```bash
cp .env.example .env        # вписать MAX_BOT_TOKEN
docker compose up -d --build
```

Приложение поднимется на `http://localhost:8099`, бот стартует автоматически.
Проверка: `curl http://localhost:8099/api/health`.

Внешних сервисов, которые нельзя поднять в Docker, решение не требует:
источники 1С, оператора ЭДО и движок маршрутизации в демо-режиме заменяют
встроенные адаптеры.

### Запуск без Docker

```bash
python -m pip install -r requirements.txt
cp .env.example .env
python run.py
```

Тесты расчётной части: `python tests/test_services.py` (10 проверок).

## Что посмотреть при проверке

1. **В чате бота** отправьте `/start`: знакомство из трёх шагов покажет живые
   цифры по компании. Затем `/money`, `/edo`, `/trips`.
2. **В мини-приложении** откройте любой рейс: там разбор себестоимости с
   формулами. Нажмите «Свой расчёт» и поменяйте пробег или ставку.
3. **Вкладка «Маршрут»**: выберите направление и машину, посмотрите на вывод
   «дешевле на N ₽, потому что …».
4. **Вкладка «ЭДО»**: готовность компании и документы с причинами отказа.

Мини-приложение внутри MAX открывается только по публичной HTTPS-ссылке,
привязку выполняют организаторы. Порядок публикации описан ниже.

## Что смоделировано

Доступа к реальной базе 1С, оператору ЭДО и движку маршрутизации у команды нет,
поэтому три интеграции работают на синтетических данных. Это видно в интерфейсе
(спокойная строка под списком рейсов и в подсказке «Четыре экрана»), в каждом
ответе API (поле `data_is_mock`) и в
[DATA-API.yaml](DATA-API.yaml).

| Интеграция | Что уже написано | Чего не хватает | Как включить |
|---|---|---|---|
| **1С** (путевые листы, ТС, водители, тарифы, ГСМ) | Адаптер OData с вынесенным маппингом полей, `backend/adapters/odata.py` | Конфигурация и тестовый доступ к базе пилота | `DATA_SOURCE=odata`, `ONEC_BASE_URL`, учётка на чтение, сверка имён реквизитов |
| **Оператор ЭДО** (статусы ЭТрН, ЭЗЗ, ЭПД) | Транспорт к API оператора, `backend/services/edo.py` | Выбранный оператор и пример ответа его API | `EDO_PROVIDER`, `EDO_API_BASE`, `EDO_API_KEY` |
| **Движок маршрутизации** | Фасад и клиент Яндекс.Маршрутизации, `backend/services/routing.py` | Ключ API или решение использовать 1С:TMS заказчика | `ROUTING_ENGINE=yandex`, `YANDEX_ROUTING_API_KEY` |

Маппинг полей 1С вынесен в отдельный файл осознанно: у перевозчиков стоят разные
конфигурации (УТ, УНФ, отраслевые ТМС), и хардкод под одну сделал бы решение
неприменимым у второго же заказчика.

### Тестовые данные

Два набора, переключаются переменной `DEMO_DATA_FILE`:

- `data/demo_1c.json` — 6 рейсов, чтобы глазами проверять формулы;
- `data/demo_1c_large.json` — год работы парка: 1200 рейсов, 40 машин,
  2330 документов ЭДО, 2070 ГСМ-накладных. Генерируется и не коммитится:

```bash
python tools/generate_dataset.py --trips 1200 --vehicles 40 --drivers 30 --months 12
```

Данные синтетические, но не случайные: расстояния считаются по координатам
реальных городов, цена литра дрейфует по месяцам, зимой в норму расхода
попадает надбавка, около 15% рейсов намеренно убыточны, около 12% с
перерасходом топлива. Набор детерминирован по `--seed`.

## Архитектура

```
frontend/          мини-приложение: HTML, CSS, JS без сборки, MAX Bridge
backend/
  main.py          FastAPI: API, раздача фронтенда, запуск бота в lifespan
  bot.py           long polling MAX, команды, знакомство, уведомления
  max_api.py       клиент MAX Bot API
  auth.py          проверка подписи initData
  db.py            SQLite: подписки, история расчётов, журнал уведомлений
  adapters/        источники данных: demo и 1С OData с маппингом полей
  services/        cost, routing, edo, tracking, catalog
data/              демонстрационные выгрузки
docs/              OpenAPI 3.1 в YAML и JSON
tools/             генератор датасета, экспорт схемы API
```

Источник правды по рейсам и документам остаётся за 1С и оператором ЭДО. Своя
база хранит только то, чего у них нет: подписки на уведомления и историю
расчётов.

Фронтенд собран без бандлера намеренно: мини-приложение раздаётся тем же
процессом, что и API, а контракт API не изменится, если UI позже переедет на
React.

## Собственное API

Мини-приложение работает только через методы этого API, 13 методов.

- Схема: [docs/openapi.yaml](docs/openapi.yaml), [docs/openapi.json](docs/openapi.json), OpenAPI 3.1.0
- Карточка API с доступами и тестовыми данными: [DATA-API.yaml](DATA-API.yaml)
- Интерактивная документация: `/docs` на запущенном сервисе
- Пересобрать схему после правок: `python tools/export_openapi.py`

Авторизация: мини-приложение передаёт подпись запуска в заголовке
`X-Max-Init-Data`, backend проверяет её HMAC-SHA256 с токеном бота. Режим задаёт
`AUTH_MODE`: `strict` для публикации, `lenient` для пилота, `dev` для локальной
разработки.

## Публикация мини-приложения в MAX

Бот не раздаёт мини-приложение через мессенджер: клиент MAX открывает адрес
браузерным движком на устройстве пользователя, поэтому `localhost` и адрес в
локальной сети не подойдут принципиально.

1. Поднять решение на публичном HTTPS-адресе (подойдёт адрес хостинга,
   свой домен не нужен).
2. Прописать адрес в `PUBLIC_WEBAPP_URL` и перезапустить сервис.
3. Отправить ссылку организаторам через форму сбора ссылок, привязку к боту
   выполняют они.
4. Переключить `AUTH_MODE` на `strict`.

Пока адрес не задан, бот это учитывает: кнопка запуска приложения скрыта, а
команда `/app` объясняет, чего не хватает. Сводки в чате работают и без
мини-приложения.

Локально интерфейс и логику можно проверять в браузере на `http://127.0.0.1:8099`.

## Поведение бота

**Знакомство.** Первое сообщение раньше было списком команд, в котором легко
запутаться. Вместо него три коротких шага с живыми цифрами: деньги, документы,
рейсы. Шаг запоминается, повторный `/start` здоровается коротко, пройти заново
можно командой `/tour`.

**Уведомления.** Два правила, без которых бот превращается в спамера:

- история не рассылается: при регистрации все накопленные поводы помечаются
  просмотренными, иначе новый подписчик получил бы 233 сообщения подряд;
- за цикл уходит одна сводка с тремя первыми пунктами и счётчиком остальных,
  а не сообщение на каждое событие.

Выключить: `/notify_off`.

AI-ассистент использовался как вспомогательный инструмент: черновики кода,

## Ограничения MVP и что дальше

- **ЭДО только на чтение.** Создание и подписание документов от имени компании
  не делается сознательно: юридически чувствительная зона. Сначала статусы и
  подсказки, автоматическое оформление ЭТрН — после пилота.
- **Телематики нет.** Перерасход топлива считается сравнением факта из путевого
  листа с нормой, а не по датчику уровня топлива. Модуль контроля на факте
  требует уже установленного оборудования у заказчика.
- **Свой VRP-солвер не пишется.** Маршруты берутся у внешнего движка, продукт
  добавляет объясняющий слой: роадбилдинг не является его ценностью.
- **Тариф Платона** задан как конфигурируемое значение (3,34 ₽/км на 1.09.2026),
  перед пилотом сверяется с действующим.
